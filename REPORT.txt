3. ГРАФ ЗАДАЧ, ВХОДЫ/ВЫХОДЫ, КЛЮЧ КЕША
--------------------------------------
Flow release-model (flow.py), стадии — отдельные задачи Prefect:
  prepare_input(data_path, config) -> {input_sha256, rows, config, cache_key}
    небольшое описание; ВЕСА/ТЕНЗОРЫ между задачами не передаются;
  obtain_artifact(workspace, manifest_name) -> manifest (пересчёт file_hashes);
  gate_check(manifest, report) | gate_check_real(...) -> решение допуска;
  publish_release_task(manifest, decision, workspace) -> исход публикации.
Кеш подготовки: @task(persist_result=True, cache_key_fn) → ключ
release.cache_key = sha256(canonical({data_sha256: file_sha256(вход),
config: весь конфиг})). Состав config учебного стенда: tokenizer_revision,
template_sha256, max_length, code_revision; реального: те же поля с реальными
значениями (real/prepare-config.json). Ключ НЕ зависит от пути — только от
байтов и конфигурации. Переживает завершение процесса (постоянный сервер
Prefect 127.0.0.1:4200, PREFECT_HOME в каталоге проекта; эфемерный режим кеш
не хранит). Повтор ВОЗМОЖЕН и нужен: чтение кеша подготовки, идемпотентный
noop публикации того же release_id, восстановление после сбоя между
указателем и журналом. Повтор ЗАПРЕЩЁН: второе событие фактического выпуска
для того же release_id, публикация без validate_release, подмена модели в
памяти работающего сервиса сменой указателя.

8. НАГРУЗОЧНЫЙ ЗАМЕР (раздел D)
-------------------------------
Условия: та же служба (backend transformers, max_concurrency=1 — семафор
вычислений), принятая baseline, CPU float32; одни и те же 8 запросов
(первые 8 golden), max_new_tokens=32 (предел протокола оценки), прогрев
выполнен до замера; клиент и сервис на одной машине, localhost.
  режим         n  успехи ошибки  время пакета  req/s   средняя   макс
  concurrency-1 8    8      0      10.751 с    0.744   1.344 с  1.587 с
  concurrency-2 8    8      0      12.454 с    0.642   2.948 с  3.568 с
Время генерации (ответ сервера): c=1 среднее 1.339 / макс 1.577 с;
c=2 среднее 1.551 / макс 1.790 с. Сырые строки с ошибками не удалялись:
real/bench-requests.jsonl (16 строк, все status=200), сводка
real/bench-summary.json, запуск logs/bench-run.log.
Очередь против вычислений: пропускная способность НЕ выросла (0.744→0.642
req/s, даже чуть ниже — генерация под load подорожала на ~0,2 с), а задержка
удвоилась (1.344→2.948 с): при параллельности 2 один запрос вычисляется,
второй ждёт семафора. Это видно по строкам: первый запрос c=2 — 1.384 с
(очереди не было), остальные 3.0–3.6 с. Рост задержки = очередь, а не
замедление модели; сервер выдерживает нагрузку без ошибок.
Prefill/decode и KV-кеш: запрос = один проход prefill по промпту (текст
отзыва + системная инструкция) + последовательные шаги decode по одному
токену; KV-кеш хранит ключи/значения уже обработанных позиций, поэтому
каждый шаг decode — O(1) внимания к прошлому, а не перепрогон промпта.
В замере ответы короткие (6–7 токенов, строгий JSON с ранним EOS), поэтому
в ~1,2–1,5 с на запрос prefill и decode сопоставимы; генерация длинных
текстов (десятки–сотни токенов) была бы на порядок дороже — не измерялось.
Почему Transformers не доказывает скорость vLLM/SGLang: HF generate —
python-цикл, одна последовательность за раз, без батчирования шагов
нескольких запросов и без paged attention; наш замер при c=2 буквально
показывает очередь (rps не вырос). vLLM/SGLang на GPU непрерывно
батчат decode-шаги множества одновременных запросов в один проход ядра —
пропускная способность растёт почти без роста задержки. Этот замер — только
латентность одного запроса одной модели на одном CPU, не бенчмарк
serving-стека; сравнение стеков требует GPU-стенда и не проводилось.

10. ОГРАНИЧЕНИЯ ИЗМЕРЕНИЙ
-------------------------
Выборка мала (8 запросов × 2 режима) — это демонстрация очереди, не
статистика; прогрев один, «холодный» старт не измерялся. Backend
последовательный (семафор max_concurrency=1) — параллельная генерация на
CPU бессмысленна (GIL + один вычислительный поток), потому параллельность 2
измеряет именно очередь. Не измерялось: длинная генерация (ответы 6–7
токенов по протоколу оценки), память/пиковое RAM, холодный кеш HF,
сеть (localhost), параллельность >2, отказоустойчивость под нагрузкой,
сравнение serving-стеков. Загрузка CPU другими процессами машины не
контролировалась (замер повторен после ремонта прогрева — первый прогон
не состоялся из-за несовместимости с transformers 5.x, исправлено до
замера; в логах оба факта).
